# Local pre-check: W4 (viewport interest, LOD, fan-out)

**Local run, not a benchmark result.** Everything ran on one laptop, and the load generator shared its CPU with the server. The benchmark runs defined in [docs/BENCHMARKS.md](../../docs/BENCHMARKS.md) happen in W9.

## Setup

| | |
|---|---|
| Machine | Intel Core i7-8750H (6 cores / 12 threads), 15.9 GB RAM, NVIDIA GTX 1050, Windows 11 |
| Server | `docker compose up` (Caddy, 1 node, Postgres 17) on Docker Desktop 29.8.0; its WSL2 VM had 12 CPUs and 7.7 GB |
| Load generator | `go run ./cmd/loadgen` on the Windows host (Go 1.25.5), connecting through Caddy at `ws://localhost:8080/ws` |
| Browser | Playwright 1.63 headless Chromium with **software** WebGL (SwiftShader), viewport 1280×800 |
| Code | commit `e96b783` plus the fan-out changes in the commit that adds this file |

## Sync latency, 200 editors on one board

Command:

```sh
go run ./cmd/loadgen -url ws://localhost:8080/ws -editors 200 -ramp 5s -warmup 3s -duration 30s \
  -ops 1 -cursor-hz 15 -hotspot 0.5 -seed 1
```

Load: 200 editors, each sending about 1 move per second (Poisson) plus 15 cursor updates per second. Half of them view the same central region; the other half are spread over a 20,000 × 20,000 area. That is about 190 batches/s in total, with roughly 100 receivers per batch.

| Build | Samples | p50 | p90 | p99 | p99.9 | max | Server-side mean¹ |
|---|---|---|---|---|---|---|---|
| Sequential fan-out, presence every tick | 264,268 | 32.2 ms | 114.6 ms | 253.8 ms | 332.8 ms | 352.3 ms | 75 ms |
| Parallel fan-out, presence every 3rd tick, encode-once cursors | 269,028 | 35.2 ms | 77.5 ms | 124.0 ms | 160.8 ms | 198.7 ms | 27 ms |

¹ `sync_server_latency_seconds` sum ÷ count: from a batch arriving at the board until its frames are queued. The commit mean was 5–6.5 ms (`board_commit_duration_seconds`).

**What the profile showed** (15 s CPU profile of the first build under this load):
- About 30% of CPU was presence (`cursorsFor`), all of it on the board actor's single goroutine: each tick it queried and sorted cursors for every client (using reflection-based sorting) and marshaled each update once per client.
- About 27% was socket write syscalls, which already run in parallel in the per-connection writers.

The second build moved presence to every 3rd tick, encoded each cursor update once per tick, and builds frames in parallel across workers.

## 100,000 objects in the browser

The board was seeded with `go run ./cmd/seed -board big100k -objects 100000` (grid layout). That created 100,000 objects in 4.1 s through the normal protocol. The browser part was measured with `npx playwright test -c perf.config.ts` ([web/perf/board.perf.ts](../../web/perf/board.perf.ts)).

| Measure | Value |
|---|---|
| Time from navigation to first objects | 2.2–2.6 s |
| Objects held by the client at 100% zoom | 72 at start, 139 after panning (of 100,000) |
| Objects held in LOD (zoomed out to show about half the board) | 48,790 |
| Frame time while panning at 100%: p50 / p95 / p99 | 1.5 / 11 / 19.6 ms |
| Frame time while panning in LOD: p50 / p95 / p99 | 0.4 / 13.5 / 320 ms |

The LOD p99 is a single frame in which newly subscribed objects caused all 49k particles to be re-uploaded. Under software rendering that upload costs about 300 ms; on a GPU it is expected to be far cheaper, but that is **not measured yet**.

Earlier LOD versions, on the same setup:
- One redrawn Graphics: p95 121 ms, p99 457 ms.
- Particles marked dynamic (re-uploaded every frame): p50 15 ms.
