# Benchmark 1: editors on one board, sync latency

**Result: the target (1,000 editors, p99 < 100 ms) was not reached on this rig.** The highest editor count with a median p99 under 100 ms was **500 (58.4 ms)**. At 1,000 editors, the median p99 was 231 ms with the default 20 ms tick. The bottleneck and what was tried are below.

**Update 2026-10-03:** the 123 ms measured here with a 50 ms tick did not replicate. Measured in pairs on the same runners, a 50 ms tick gives 168–192 ms against 180–222 ms for 20 ms; see [2026-10-03-adaptive-tick.md](2026-10-03-adaptive-tick.md). Busy boards (over 500 clients) now slow their tick toward 50 ms on their own.

Method: [docs/BENCHMARKS.md](../../docs/BENCHMARKS.md), scenario 1. Raw files for every run (setup record, loadgen summary, HDR histogram log, the node's own stats every 10 s) are in [2026-10-02-sync/](2026-10-02-sync/).

## At 1,000 editors: what was found and tried

**Where the time goes.** These come from CPU profiles taken on the runner, 30 s inside the measured window (`node-cpu.pprof`, from the workflow artifacts):
- About **40% is socket writes.** Each client gets one WebSocket frame per tick that has news for it: up to 50 frames/s per client, so about 50,000 `write` syscalls/s at 1,000 editors.
- About **17% is reads.** There are 15 cursor messages/s per editor.
- **Frame building**, mostly cursor fan-out, was 45% of node CPU in the first local profile. Cursor fan-out is 20% after the two changes below.
- The node averaged 1–1.3 of its 2 cores. Latency therefore comes from bursts and queueing, not from steady saturation. The node's own p99 (from receiving a batch until its frames are queued) was already 94–675 ms in 10-second windows, while its p50 stayed near 21 ms.

**Changes made during W9.** Each one has its own commit.
1. **Nearest cursors computed once per view.** Choosing each client's 30 nearest cursors is now done once per snapped view per presence tick and shared, using quickselect instead of a sort (`2a6f664`).
2. **Pre-encoded cursor moves.** A client that was shown exactly the shared set last time gets that set's moved cursors as one pre-encoded slice (`25a8e6b`).
3. **One write deadline for many writes.** Writes reuse a deadline context instead of allocating one per frame, which had cost 7% of node CPU (`25a8e6b`).
4. **Snapshots at most once a minute.** Before this, snapshots ran every 5,000 batches, which here meant every ~5.6 s. Each one copied ~80k objects on the board's goroutine (`986a3bd`).
5. **A lighter load generator.** Its clients no longer keep replicas or Welcome snapshots. Before this, the 1,000-editor trial was invalid (loadgen CPU 74%) and a 1,500-editor runner ran out of memory (`a49ff91`, `3fc8e7a`).

**Re-runs at 1,000 editors, 3 runs each:**

| Build and tick | Median p99 | p99 of each run | p50 of each run | Node CPU |
|---|---|---|---|---|
| `3fc8e7a`, tick 20 ms (sweep above) | 267.0 ms | 256.5, 267.0, 441.9 | 33.9–38.5 ms | 82–128% |
| `986a3bd` (snapshots ≤ 1/min), tick 20 ms | 231.4 ms | 212.1, 231.4, 295.7 | 25.7–37.2 ms | 96–132% |
| `e168de2`, tick 33 ms | 208.0 ms | 164.1, 208.0, 227.8 | 33.7–37.7 ms | 76–107% |
| `e168de2`, tick 50 ms (did not replicate; see the update above) | 122.8 ms | 99.9, 122.8, 184.8 | 38.4–49.2 ms | 53–87% |

A longer tick means fewer, larger frames per client, so fewer syscalls and less contention. The cost is a longer wait for every edit: p50 rises with the tick. The node's own p99 at tick 50 ms was 58–132 ms per 10-second window. Its floor is roughly one tick plus the commit (2–3 ms), so a 50 ms tick cannot get much lower. The default stays at 20 ms, which gives the lowest latency up to 500 editors.

**Not reached, and why.** At 1,000 editors in this scenario, 500 people share one viewport. Every edit there goes to about 500 receivers, and every client gets frames at the tick rate. On 2 cores, the per-frame syscalls and the scheduling of 1,000 writer goroutines produce a tail above 100 ms. Ideas not tried yet:
- An adaptive tick that lengthens only under load (done on 2026-10-03: −12% p99 at 1,000 editors; [results](2026-10-03-adaptive-tick.md)).
- Batching several frames into one write per client.
- Fanning out through edge nodes (ADR-0005's "later scope"), so that one node does not write to every socket.

**Limits of this rig.** On a free 4-vCPU runner, the loadgen gets only 2 cores. At 1,500 and 2,000 editors it used 75–91% of them, so those runs are invalid under the method's 70% rule. Load beyond 1,000 editors therefore cannot be measured validly here.
