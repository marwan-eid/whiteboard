# Benchmark 5: failover under load

**Result: across 12 runs, no acknowledged edit was lost and none was duplicated.** With the final code:
- **Killed node** (SIGKILL): 99% of editors were receiving frames again 4.0–4.9 s later.
- **Node paused for 10 s:** 7.6–8.0 s later.

Method: [docs/BENCHMARKS.md](../../docs/BENCHMARKS.md), target 5. Raw files for every run (setup, the checker's output, the per-second timeline, the HDR histogram) are in [2026-10-03-chaos/](2026-10-03-chaos/).

## Setup

| | |
|---|---|
| Rig | GitHub Actions `ubuntu-24.04` (4 vCPU), one runner per run, via [.github/workflows/chaos.yml](../../.github/workflows/chaos.yml) |
| Server | `compose.yaml`: **2 nodes** (the method asked for 3; the Compose stack has 2), Postgres and Caddy, with 5 s leases. No core pinning: the load generator shares the runner. |
| Load | [loadgen/scenarios/editors.yaml](../../loadgen/scenarios/editors.yaml) with 250 editors through Caddy: a 30 s ramp, then 210 s of editing. The board was seeded with 10,000 objects. |
| Event | At T+120 s the node serving the board, found through the route API, was killed (`docker compose kill -s SIGKILL`) or paused for 10 s (`docker compose pause`/`unpause`). |
| Checks | [cmd/chaoscheck](../../cmd/chaoscheck):<br>• Every batch the load generator saw acknowledged must be in the log, live rows or compacted segments, exactly once.<br>• **Recovery** is the time from the event until the first second in which 99% of editors received a frame. |

## Results

**Final code** (commit `894b947`: client watchdog plus Caddy health checks):

| Run | Acknowledged | Lost | Duplicated | Recovery | p99 per second, before | Worst p99 per second, during recovery |
|---|---|---|---|---|---|---|
| kill 1 | 55,134 | 0 | 0 | 4.9 s | 27.3 ms | 5,091 ms |
| kill 2 | 54,239 | 0 | 0 | 4.0 s | 143.1 ms | 4,416 ms |
| kill 3 | 55,417 | 0 | 0 | 4.0 s | 29.1 ms | 4,284 ms |
| pause 1 | 55,546 | 0 | 0 | 8.0 s | 27.6 ms | 7,914 ms |
| pause 2 | 55,575 | 0 | 0 | 7.6 s | 25.1 ms | 7,815 ms |
| pause 3 | 55,036 | 0 | 0 | 7.7 s | 27.7 ms | 7,721 ms |

**How to read the numbers:**
- **The log always held a few more batches than were acknowledged.** For example, 55,154 against 55,134. These were committed just before the kill, but their acknowledgements never arrived. The clients resent them and the server recognized them as already applied, which is why nothing is duplicated.
- **"During recovery" latency is large by design.** Edits made while a client had no server are delivered once it reconnects. Their latency includes the outage, which is the right way to count them.

## What the runs found, and what changed

The first runs (commit `0ba63ce`, in `first-0ba63ce/`) also lost nothing:
- Recovery from a kill took 3.5–5.7 s.
- Recovery from a 10 s pause took **10.9–11.2 s**, about the length of the pause.

A frozen node's TCP connections stay open, so clients never noticed it and waited for it to come back. Two changes followed:
1. **Clients leave a silent server** (commit `fd43617`). The web client drops the connection when nothing arrives for 6 s after the welcome, while pinging every 2 s. The Go client and the load generator got the same check (`Config.Liveness`). Pause recovery was still 10.2–12.5 s (`pause-watchdog-only-fd43617/`).
2. **Caddy health-checks nodes** (commit `894b947`). The kernel of a frozen container still accepts TCP connections, so Caddy kept sending reconnecting clients to it and waited with no timeout. Every proxy now checks `/healthz` every second with a 1 s timeout, and has dial and response-header timeouts. Pause recovery fell to 7.6–8.0 s.

The floor for a pause is roughly the 6 s watchdog plus a few seconds to reconnect, find the new owner and load the board.
