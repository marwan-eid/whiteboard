# Benchmark 2: 100,000 objects in the browser

**Local run on one laptop, one run per case. These are measurements on stated hardware, not a fleet benchmark.** Method: [docs/BENCHMARKS.md](../../docs/BENCHMARKS.md), target 2. Raw output: [2026-10-02-browser-100k/](2026-10-02-browser-100k/).

**Result:** with the laptop's GPU and no throttling, frame time while panning met the "smooth" bar: p95 5.9–6.8 ms against 16.7 ms. With 4× CPU throttling it did not: p95 42–47 ms.

## Setup

| | |
|---|---|
| Machine | Intel Core i7-8750H (6 cores / 12 threads), 15.9 GB RAM, Windows 11. Chrome rendered on the **integrated Intel UHD Graphics 630** (Direct3D 11 through ANGLE), not the laptop's GTX 1050. |
| Browser | Chromium 153.0.8010.12 (Playwright 1.63), in a real window (the `gpu` project in [web/perf.config.ts](../../web/perf.config.ts)), viewport 1280 × 800 |
| Server | `docker compose up` (Caddy and 2 nodes) on Docker Desktop, on the same laptop |
| Boards | 100,000 objects each, seeded with `cmd/seed` through the normal protocol: `big100k-grid` (`-layout grid`) and `big100k-clustered` (`-layout clustered`) |
| Script | [web/perf/board.perf.ts](../../web/perf/board.perf.ts):<br>1. Load the board.<br>2. Pan 120 wheel steps at 100% zoom.<br>3. Zoom out until LOD mode.<br>4. Pan 60 steps in LOD.<br>Frame times come from the app's on-demand renderer; frames only render when something changed. |
| Code | commit `e168de2` (the web client is unchanged since W8) |

## Results

| Board | CPU throttle | First objects shown | Bytes before first objects | Objects held: start / after pan / in LOD | Pan p50 / p95 / p99 | Zoom-out frames p95 | LOD pan p50 / p95 / p99 | JS heap at end¹ |
|---|---|---|---|---|---|---|---|---|
| grid | none | 1,290 ms | 7.5 KB WebSocket + 227 KB HTTP | 72 / 123 / 87,492 | 0.9 / **5.9** / 14.3 ms | 22.8 ms (6 frames) | 0.2 / 0.8 / 26.9 ms | 37 MB |
| clustered | none | 740 ms | 2.0 KB WebSocket + 227 KB HTTP | 19 / 242 / 75,901 | 0.8 / **6.8** / 10.8 ms | 19.1 ms (6 frames) | 0.2 / 0.4 / 36.1 ms | 35 MB |
| grid | 4× | 1,589 ms | 7.5 KB + 227 KB | 72 / 123 / 87,492 | 7.3 / **47.4** / 73.0 ms | 514.9 ms (6 frames) | 1.4 / 3.4 / 124.6 ms | 207 MB |
| clustered | 4× | 2,097 ms | 2.0 KB + 227 KB | 19 / 242 / 75,901 | 5.8 / **41.8** / 68.8 ms | 545.2 ms (7 frames) | 1.2 / 2.6 / 121.3 ms | 201 MB |

¹ Chrome's `performance.memory.usedJSHeapSize`, read once at the end. It is coarse, and depends on when GC last ran.

**What the numbers say:**
- **Only the visible region is loaded.** The client holds 19–242 of 100,000 objects at 100% zoom, and the first render needs 2–7.5 KB of board data.
- **Zooming out is the expensive moment.** Entering LOD subscribes to 76–87k objects at once. That produced a single 19–23 ms frame on the GPU, and a 515–545 ms frame under 4× throttling. In LOD, each pan step brings new objects, which caused one frame of 27–36 ms (121–125 ms throttled).
- **Throttled panning is not smooth:** p95 42–47 ms.

## Server side: viewport queries on the 100k grid

`BenchmarkQueryViewport100k` in [internal/spatial/grid_test.go](../../internal/spatial/grid_test.go) queries a 2880 × 1620 viewport (1920 × 1080 plus a 50% margin) at random positions on a 100,000-object grid, with the board's grid settings. It ran in a `golang:1.25` container on the same laptop, as 3 runs of 20,000 queries each:

| p50 | p99 | Mean |
|---|---|---|
| 37.6–38.0 µs | 78.7–87.8 µs | 39.9–40.5 µs |

Moving one object in the same grid takes 226–260 ns (`BenchmarkMove100k`).
