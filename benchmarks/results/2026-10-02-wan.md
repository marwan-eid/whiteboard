# WAN: editors over the internet against the live demo

**One run, over the public internet. Labeled WAN, as docs/BENCHMARKS.md asks: it measures what a user would see, not the server's capacity.** Raw files: [2026-10-02-wan/](2026-10-02-wan/).

## Setup

| | |
|---|---|
| Server | The public demo at the time: the **fallback** deployment on Oracle's Always Free AMD Micro VM (`VM.Standard.E2.1.Micro`: 1/8 OCPU guaranteed, 1 GB RAM, 2 GB swap), in eu-amsterdam-1. It ran 2 nodes, Postgres and Caddy (`deploy/compose.small.yaml`). The A1 VM was unavailable for lack of capacity; see ADR-0006. |
| Client | `cmd/loadgen` on a laptop (Intel Core i7-8750H, Windows 11) on a home connection. The TCP connect time to the server was 62–67 ms, so one round trip is about 62 ms. |
| Scenario | [loadgen/scenarios/editors.yaml](../../loadgen/scenarios/editors.yaml) with **50 editors** (the demo allows 64 sockets per IP), a 20 s ramp, 10 s warm-up and 60 s measured, over `wss://` through Caddy. |
| Latency | From the sending editor writing a batch until another editor receives it. Both run on the laptop, so each sample includes the trip to the server and back. |

## Result

| Samples | p50 | p90 | p99 | p99.9 | max |
|---|---|---|---|---|---|
| 31,978 | 99.6 ms | 156.8 ms | 229.8 ms | 312.3 ms | 331.5 ms |

**How to read it:**
- **Most of p50 is the network.** One round trip is about 62 ms. On top of that come up to one 20 ms tick and the commit on a 1/8-OCPU VM.
- **Server CPU during the run was not recorded.** The container stats I took were sampled after the run had ended.
- **This reflects the fallback VM, not the A1 setup.** It will be re-run on A1 if A1 capacity frees up.
